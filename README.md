# Window Placement (Transport Fever 3)

A small UI mod for Transport Fever 3 that makes **new entity windows open next
to already pinned entity windows** instead of on top of them in the top-right
corner, the way Transport Fever 2 did it.

- Windows fill columns from the right screen edge. If there is enough vertical
  space (e.g. at 50 % UI scale on a tall screen), a second row below is used
  first.
- All sizes are measured live (window width/height, screen size, game bar),
  so it works with any resolution and UI scale.
- Unpinned windows do not block a slot: the next window takes the place of
  the previous unpinned one, and only moves on once you pin.
- Purely cosmetic: achievements stay enabled.
- English and German.

Available on mod.io: <https://mod.io/g/transportfever3/m/window-placement>

Known limitations: a pinned window that you drag elsewhere keeps blocking its
original slot; pinned windows restored from a savegame are placed in order,
not at their saved positions.

## Installation

Subscribe on mod.io or in the in-game Mod-Hub, then enable the mod when
loading or creating a game.

Manual installation: copy the folder `kampfmoehre_window_placement_1` into
the game's local mod directory, on Linux
`~/.local/share/Steam/userdata/<steam-id>/3493540/local/mods/`.

## How it works

Transport Fever 3's UI is written in Lua/Teal on top of an in-house,
React-like component system. The base game hardcodes
`initialX = 1, initialY = 0` for every entity window in
`gui/entity_window/view_manager.tl`. Mods cannot replace that file, but they
can hook into the UI through `react-plugin` resources:

- `entry.res.lua` registers a plugin at the game's `ModEntryPointExtension`,
  which loads `window_placement.script.lua` into the GUI Lua state as soon as
  the game UI is built.
- The script wraps `builtin.Window`. For windows with `tool = "entityWindow"`
  it computes a free slot and overrides `initialX`/`initialY` (screen
  fractions; entity windows are anchored at their top-right corner).
- Open windows are tracked in a small registry; `react.onUnmount` removes
  them when the game closes or replaces a window.

Tunables at the top of the script: `GAP_REDUCTION_FRACTION` and
`VGAP_REDUCTION_FRACTION` (spacing between windows, as a fraction of the
window width), `FILL_ORDER` (`"columns"` or `"rows"`), `MIN_RIGHT_EDGE`.

## Development

```
kampfmoehre_window_placement_1/    the mod (this is what gets published)
  mod.json                         mod id
  _metadata/modinfo.json           name, summary, description (+ de)
  _metadata/0.png                  title image, 1920x1080
  content/gui/kampfmoehre_window_placement/
    entry.res.lua                  plugin registration (entry point)
    window_placement.script.lua    the actual code
sync.sh                            copies the mod into the game's staging area
```

Workflow (Linux):

1. Edit the files in `kampfmoehre_window_placement_1/`.
2. Run `./sync.sh`. It copies the mod into the game's staging area
   (`.../userdata/<steam-id>/3493540/local/staging_area/`), where the game
   loads it as a development mod. Returning to the main menu and reloading
   the savegame is enough to pick up changes, no restart needed.
3. Lua errors show up as a red error screen in the game ("Copy to clipboard")
   and in `.../3493540/local/crash_dump/stdout.txt`. The script logs with the
   prefix `[window_placement]`, one line per newly placed window.
4. Before uploading a new version through the in-game Mod-Hub, increase
   `revision` in `mod.json`. mod.io rejects a package whose content is
   byte-identical to an already uploaded one.

The staging copy also contains files generated by the game (`.cooked_*`,
`_metadata/mod.io_fileid.txt`). `sync.sh` leaves them alone and they are
ignored by git.
